# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — dev server (with `--host`). Needs the local PocketBase (`docker compose up -d`) to show any content; without it the site still runs, minus its projects and reviews (see "When PocketBase is unreachable").
- `npm run build` — runs `astro check` (type-checking, must stay at 0 errors) then builds for the Vercel serverless adapter
- `npx astro check` — type-check only
- `docker compose up -d` — local PocketBase at http://127.0.0.1:8090 (dashboard at `/_/`, superuser `thomas@gysemans.dev` / `thomasgysemans`). Schema migrations are versioned in `db/pb_migrations/` (excluded from tsconfig).
- `node scripts/seed-pocketbase.mjs` — wipes and re-seeds the content collections (target/credentials via `POCKETBASE_URL`, `PB_SUPERUSER_EMAIL`, `PB_SUPERUSER_PASSWORD`). The seed content itself lives in `scripts/seed-data.mjs`.
- `npm run test` / `npm run test:unit` — Vitest unit tests (`tests/unit/`), configured via `getViteConfig` in `vitest.config.ts` so the `@i18n`/`@data` aliases and the `astro:i18n` virtual module resolve. Pure logic only (no DB).
- `npm run test:e2e` — Playwright e2e tests (`tests/e2e/`). **Requires the local PocketBase running with seeded content.** Playwright's `webServer` starts the dev server via `dev:e2e` (`astro dev` daemonises when stdout is not a TTY, so it starts the daemon then tails its logs to stay foreground).

Running a subset:
- `npx vitest run tests/unit/projects.test.ts` — one unit file; `-t "pattern"` narrows to matching test names; `npm run test:unit:watch` for watch mode.
- `npx playwright test tests/e2e/i18n.spec.ts` — one e2e file; `-g "pattern"` by title, `--headed` / `--ui` / `--debug` to watch it run.

**The tests must never alter the data.** They hit a real PocketBase but strictly read-only: only `GET` requests, with the sole exception of the login-specific requests (which authenticate, they don't mutate content). Never write a test that creates, edits or deletes a project, review, technology or any other record.

`tests/unit/schema-sync.test.ts` is the one to know about: it **replays every migration in `db/pb_migrations/` in a stub PocketBase runtime** (no database) and asserts the `select` fields still match the typed dictionaries. A value added through the PocketBase dashboard without its fr/en labels would otherwise render as a raw identifier on the live site — so a schema change made in the dashboard means updating `categories.ts` / `technologies.ts` / `models.ts` in the same commit.

No linter is configured. Node 24.x (`engines`). The only required environment variable is `POCKETBASE_URL` (`pb.ts` throws on import without it). The quote form's SMTP account is set by the five `QUOTE_EMAIL_*` variables (sender, its password, host, port, receiver), declared as optional secrets in the `env.schema` of `astro.config.ts`: read at runtime through `astro:env/server`, never inlined in the bundle, and when one is missing only the form fails (503), not the site. They must also be set in the Vercel project. The `SUPABASE_*` keys still sitting in `.env` are leftovers from a previous storage backend and are referenced nowhere.

## Conventions

- Answer in French, keep technical terms in English. Explain your changes simply.
- Code and comments in English. The owner usually commits himself: commit only when he asks, and then never push, keep the message short with a prefix (`feat:`, `fix:`, `doc:`…), and add no AI co-author line.
- Project slugs must stay stable: they match the URLs of the production site (SEO).
- **Never delete or modify `public/cv.pdf`**, even if it looks unreferenced.

## Architecture

Astro 7 in SSR mode (`output: "server"`, Vercel serverless adapter imported from `@astrojs/vercel`) + Svelte 5 islands + Tailwind 4. The public design is the "star chart" (prototype v3, see `DESIGN.md`): a deep-space page with a fixed starfield, planets drifting behind the content and hairline drawings. `/showcase` predates it and is deliberately kept as it was.

### Middleware pipeline (`src/middleware.ts`)

`sequence(clientIPMiddleware, userMiddleware, adminMiddleware)` — Astro's own i18n middleware runs around this automatically (see below).

- **`clientIPMiddleware` runs first and must stay first.** Every PocketBase call leaves from the server, so PocketBase's per-IP rate limiting would see all visitors as one bucket. The visitor's IP is stashed in an `AsyncLocalStorage` (`src/data/client-ip.ts`) and every PB client forwards it as `X-Forwarded-For` via a `beforeSend` hook. **`AsyncLocalStorage`, not a variable or a `locals` field**, because Astro streams: the data fetching in a page's frontmatter happens *after* the middleware chain has returned, and the public `pb` client is a module-level singleton shared by concurrent requests — so the IP must be resolved at send time, not captured eagerly. PocketBase only trusts the header once it is listed in Settings → Application → user IP proxy headers.
- `userMiddleware` resolves the locale (below) and the `theme` cookie, which only the back-office reads (the public site is dark only); `adminMiddleware` gates `/admin*`.
- `security: { checkOrigin: true }` in `astro.config.ts` — the back-office form POSTs depend on it.

### i18n (unusual setup — read before touching routing)

- **There is no `src/pages/en/` folder.** Pages exist once, without locale prefix. `/en/*` URLs work through Astro's **native** i18n: `astro.config.ts` sets `routing: { prefixDefaultLocale: false, fallbackType: "rewrite" }` with `fallback: { en: "fr" }`, so Astro renders the shared (fr) pages in place at the `/en/*` URLs while `Astro.currentLocale`/`locals.lang` stay `en`. **This is not `routing: "manual"`** — Astro's i18n middleware runs automatically and is no longer added to the `sequence()` by hand.
- **Language redirection** (in `userMiddleware`): only the prefix-less URLs are ambiguous entry points that may be redirected. A first-time visitor on a default URL is sent to their preferred locale — the `lang` cookie (their past explicit choice) first, else the browser's `Accept-Language` (parsed by `preferredLocale` in `config.ts`). A `/en/*` URL is an explicit request and is **never** redirected (crawlers included → both versions stay indexable). `/admin`, non-GET, non-HTML and `/_*` requests are skipped. The `if (context.locals.lang) return next()` guard avoids re-processing when the fallback rewrite re-runs the chain.
- **The `lang` cookie is the explicit choice**, set for a year: written by the language switch client-side (`[data-set-lang]` in `Header.astro`, before navigation) so the switch is authoritative and never bounced, and mirrored server-side to the locale actually served.
- Everything i18n lives in `src/i18n/`: `config.ts` is the single source of truth for locales + `preferredLocale` (imported by `astro.config.ts`, the middleware, and `App.LangCode` in `env.d.ts`); copy is split per page namespace in `translations/` and consumed as `trans.section.key[lang]` via `import trans from "@i18n"`.
- Data files must import from the `@i18n/text` subpath (not `@i18n`), because the index re-exports `paths.ts` which depends on the `astro:i18n` virtual module.
- `Astro.locals.lang` is the only way pages know the language.

### Theming

The public site is **dark only**, on purpose (the night sky is its identity). All its colours are CSS variables declared on `:root` in `src/styles/tailwind.css` and exposed to Tailwind 4 through `@theme` (CSS-first config, there is no `tailwind.config.mjs`): style with token classes (`text-heading`, `bg-panel`, `border-line`, `bg-accent`, `text-accent-text`…) or `var(--…)` in scoped styles, never hardcoded theme colours. Named text styles (`heading-1`…`6`, `title-*`, `body-*`, `caption-*`, `button-*`) and layout classes (`wrap`, `section`, `split-head`, `card`, `btn`, `eyebrow`, `reveal`…) live in its `@layer components`. The old numeric scale (`text-xs`…`text-3xl`) and a few legacy colour names (`night`, `outline`) are kept only because `/showcase` and the back-office islands use them.

`/showcase` keeps its previous look through `.theme-showcase` (body class set by `ShowcasePage`): white text, its old accent and focus ring, but the site's Geist face. The back-office has its own light/dark themes (`theme` cookie, `data-theme` on `<html>`) and its own stylesheet (`src/styles/admin.css`), which remaps the public variables (`--bg`, `--heading`, `--accent`…) onto its palette inside `body.adm`.

**Motion.** `data-motion` on `<html>` is set before the first paint by an inline script of `PageLayout`: `"reduce"` when the visitor paused the animations with the floating button (`MotionToggle`, remembered in `localStorage`) or when the system asks for reduced motion. CSS reads the attribute; scripts use `src/lib/motion.ts` (`motionOK()`, `onMotionChange()`), which also drives the project videos (`thumb-video.ts`). The planets' parallax is the exception: it follows the scroll rather than a clock, so the pause button leaves it (pausing must not make the planets jump) and only the system setting turns it off.

### Data

`src/data/` is the **PocketBase-backed data layer** (dev and prod both hit a real database; `POCKETBASE_URL` is mandatory). `pb.ts` holds the client (`autoCancellation(false)` for SSR) and the cache; the async functions (`getAllProjects`, `findProject`, `getFeaturedProjects`, `getProfessionalProjects`…) map records to the models of `models.ts`, building `Localized` fields from the `project_translations` rows (en falls back to fr) and image URLs through PocketBase's thumb API (`800x0` for cards, `1200x0` for detail — only sizes declared on the file field work; `pictures` has no declared sizes and is served full-size). The project flagged `carousel` in `/admin` (one at most; the field name is historical) is the wide headline card of the homepage's Work section; the next two featured projects follow it.

The `cached()` helper is more than a 60s TTL, and the extras are load-bearing: **single flight** (one in-flight promise per key — the homepage needs featured/carousel/count, all derived from the same list, so a cold cache would otherwise fire several identical queries) and an **epoch counter** bumped by `invalidateCache()`, so a load started before an admin mutation cannot write its stale result into the freshly-cleared cache when it resolves.

**When PocketBase is unreachable** (down, timing out after 5 s, 5xx behind nginx, 429), nothing crashes. `cached()` keeps expired entries and serves the last loaded copy; with nothing loaded yet it throws `ContentUnavailableError`, and stops asking PocketBase for 10 s (`RETRY_MS`) so an outage does not cost every render a timeout. Any other error (a bad filter, a 403) is a bug and still throws. Pages decide what an outage means through `ifAvailable()` (undefined instead of the error): the homepage renders without its Work section and project count, while `/projects`, `/showcase` and a project page answer **503** (`ErrorPage status={503}`, `Retry-After`), never an empty 200 or a 404 that search engines would take for the real page, and the sitemap answers 503 too. That is why those routes load their data in `src/pages/` and pass it down as props, like the project page always did: the route picks the page or the 503 before anything is rendered, and the status must be set before the first byte streams out.

**`getAllProjects()` is the single choke point of every public read**: it filters `hidden != true` once, so a hidden project disappears from the cards, showcase, carousel, sitemap and its own detail page (404) at the same time. Derive from it rather than querying the `projects` collection directly.

A project's presentation picture (`thumb`, required) may be doubled by an optional **looping muted video** (`thumb_video`): it plays in its place on every card of the site. The image is deliberately kept required alongside it, because it is the video's `poster`, the reduced-motion fallback *and* the OG/Twitter card of the project page — a video can be none of those. Every card rendering goes through `ProjectThumb.astro` / `ProjectThumb.svelte` (same markup, one per world), and `src/lib/thumb-video.ts` drives playback (and pauses with the pause button): the markup ships **without a `src`** and an `IntersectionObserver` assigns it on entering the viewport, so a grid of twenty cards downloads only what is on screen. Astro's cards are scanned once (`data-thumb-video` + `mountThumbVideos()`); the islands' cards, created and destroyed by the filters, register through the `thumbVideo` action instead — never both, or a filtered-out card would stay observed.

A project's media list holds **three kinds of media in one display order**: uploaded images, uploaded videos and YouTube links. The first two live in the `pictures` file field, told apart by extension via `isVideo()`; a YouTube link cannot (a file field only stores files) and lives in the `picture_embeds` JSON column instead, each entry recording the `position` it occupies in the merged list. `mergeMedia()` rebuilds that one order — embeds claim their index, files fill the rest — and is called by *both* `mapProject()` and the back-office `projectFormState()`, so the editor always shows what the site renders. All of it is in `data/media.ts`, which must stay free of PocketBase imports because it is also bundled client-side by the `MediaUploader` island; `youtubeId()` there is the single URL parser *and* validator, on the client and on the server. Per-picture fr/en captions live in a `picture_captions` JSON column keyed by the filename for an upload and by the link itself for an embed (pages fall back to the project's `caption`).

The project page renders the three kinds differently: a lazy `youtube-nocookie.com` iframe for an embed, a native player for a video, and a zoomable picture for an image (only images open the lightbox — so `lightboxIndex` counts images only). `pictures` stays **required** by the collection, so a project can never have a YouTube link as its only media (the back-office rejects that before writing).

Collections: `projects` (+ selects `categories` — **multi-select**, a project may belong to several ones —, `context` = `personal|school|professional`, `languages`), `project_translations` (unique per project+locale), `project_techs` (junction with `role` and 1-based `position` — PB treats 0 as blank on required numbers), `technologies` (lowercase hex `color` enforced by pattern, `group` select), `reviews` (flat `_fr`/`_en` columns). Select identifiers are stored in the DB; their fr/en labels live in `categories.ts` (`CATEGORIES`, `CONTEXTS`, `TECH_ROLES`) and `technologies.ts` (`GROUP_TITLES`).

### Page pattern

`src/pages/*.astro` are thin wrappers (the ones that need PocketBase load the data and pass it down, see above); real pages live in `src/components/pages/*.astro` (`ErrorPage` serves both the 404 and the 503); the homepage's sections are in `src/components/home/` (Hero, WhyMe, Tagline, Work, About, Method, Compare, Pricing, Faq, Launch); interactive parts are Svelte islands in `src/components/svelte/` only where state is rich (`ProjectsExplorer`, `ImageLightbox`, `ShowcaseViewer`), plain `<script>`s otherwise. Islands receive **pre-localized strings** as props — locale resolution always happens server-side — and cannot use `astro-icon`, so they draw the few icons they need through `PhIcon.svelte`. Icons are Phosphor SVGs in `public/icons/`, served by `astro-icon`.

Layouts nest: `PageLayout` is the `<html>` shell (all the SEO, the motion script, the preloaded fonts), `MainLayout` wraps it with `SpaceBackdrop` (stars, twinkles, planets), the `Header`, the `Footer` and the `MotionToggle`, and is what public pages use. `/showcase` uses `PageLayout` directly.

**The planets and the rocket are hand-written WebGL, not three.js** (`src/lib/space/`: `gl.ts` parses the GLB files and holds the matrices and camera, `planets.ts` the fixed planets canvas, `rocket.ts` the launch pad, `sky.ts` the starfield, `loop.ts` the shared `requestAnimationFrame`). Keeping three.js out of the public pages is what keeps the mobile Lighthouse score up. Nothing 3D competes with the first paint: the planets' context is created once the page has loaded and the browser is idle, and each model (`public/models/*.glb`, a few hundred flat-shaded triangles) is fetched only when its body comes within about a screen of being seen, one at a time. Each page places its own bodies through `MainLayout`'s `planets` prop (`PlanetPlacement`: anchor element, fraction of its height, fraction of the screen width, phone variants); their look lives in the presets of `planets.ts`. Three.js/Threlte remain only in `/showcase` (`ShowcaseViewer` + `Nebula`, fixed-dark).

**The quote form mails Thomas directly**, through the `sendQuote` Astro Action (`src/actions/index.ts`, nodemailer over SMTP): from `QUOTE_EMAIL_SENDER` to `QUOTE_EMAIL_RECEIVER`, with the visitor's address as `Reply-To`, written in French whatever the visitor's language (which the mail states). `Launch.astro` checks the request in the browser (one or more types, the idea, the visitor's email; deadline and budget are optional) and the action checks it again with zod; both read the same rules from `src/lib/quote.ts`, which also composes the mail. The rocket lifts off only once the server confirms; a failure keeps the form filled and names the direct address. Without JavaScript the form posts to the page (`action={actions.sendQuote}`) and `Astro.getActionResult()` renders the outcome. Abuse guards: a honeypot field (`website`, answered with a fake success) and at most 5 requests per IP and hour (in memory, per instance). **Never submit a valid form in a test or a manual check without filling the honeypot**: it sends a real mail (and the action is called at `/_actions/sendQuote/`, with a trailing slash, so a route mocking `/_actions/sendQuote` misses it).

`/freelance` is a 301 to the homepage (its pitch, pricing and FAQ now live there), kept for old links and search engines, in each language.

### SEO

All of it is centralised in `PageLayout.astro` (canonical, OG/Twitter, hreflang, JSON-LD `Person`) — pages only pass `title`/`description`/`image`/`noindex`. The homepage adds a `FAQPage` JSON-LD built from the same `faq` array as the visible questions, so both always match. Two rules the whole setup hangs on, and both are easy to break by accident:

- **Each language version is self-canonical**, so both stay indexable. Under the i18n fallback *rewrite* `Astro.url.pathname` has already lost its `/en` prefix, so the canonical is rebuilt from the served locale with `pathInLocale()` — never from the raw pathname.
- **`pathInLocale()` drops the trailing slash** (except at the root), which is what makes the canonical URLs, the hreflang alternates and the sitemap agree on one single URL form per page. `alternateLinks()` adds `x-default` → default locale.

`src/pages/sitemap.xml.ts` is an **SSR route** (`prerender = false`), so it always reflects the current PocketBase content without a rebuild: one `<url>` per locale variant, each carrying the full hreflang set, with `<lastmod>` from the project's `updated` (listing pages use the most recent one). Social card defaults to `/og-fr.png` or `/og-en.png` (1200×630) depending on the served locale. Bots (link-preview scrapers, crawlers) are never language-redirected, so a shared link to `/` always previews the French card.

Self-hosted variable fonts (`public/fonts/*.woff2`, raw sources gitignored): **Geist** and **Geist Mono** for the whole public site, `/showcase` included. `PageLayout` preloads Geist only.

### Back-office (`/admin`)

PocketBase-superuser-only CMS for projects, technologies and reviews — no separate admin app, it's Astro pages under `src/pages/admin/` rendering `src/components/pages/admin/*.astro`, sharing `AdminLayout.astro` (French-only, `noindex`, no SEO tags). Server logic lives in `src/data/admin/`:
- `client.ts` — login exchanges superuser credentials for a token (`adminLogin`); the token is stored in an **httpOnly** cookie (`admin_token`), never in the shared public `pb.ts` client. `adminFromCookies()` rebuilds an authenticated client per-request and validates `isSuperuser`.
- `forms.ts` — shared FormData/PocketBase-error helpers used by the POST handlers, plus the async protocol (`isAsyncRequest`, `formResponse`, `failure`, `pbFieldErrors`).
- `explorer.ts` — the sidebar's list of projects/reviews, loaded by `AdminLayout` on every page.
- `projects.ts` / `reviews.ts` — parse form values, write the project + its French/English translations + tech junctions (or the review), and call `invalidateCache()` from `pb.ts` so the public site reflects the change immediately on that instance.
- There is no `admin/technologies.ts`: that collection is small enough that its CRUD lives inline in `src/pages/admin/technologies.astro`.

**Form convention (no API routes):** each `src/pages/admin/**.astro` handles its own `POST` in the frontmatter — `if (Astro.request.method === "POST")` → parse `formData` → write → `invalidateCache()` → a `FormResult` (`{ redirect }` or `{ error, fields, values }`, see `data/admin/forms.ts`). `Astro.locals.admin!` is the authenticated client (the middleware guarantees it is set). A file input can express "replace" but never "delete", so the optional `thumb_video` is cleared through its own `thumb_video_remove` checkbox (the handler then writes `thumb_video: null`). Two islands live inside the project `<form>`: `MediaUploader.svelte` (drag & drop ordering of uploaded + staged files, per-row caption inputs and `picture_order` hidden inputs) and `TechsEditor.svelte` (the techs list is saved **with** the project, marker `techs_present`: the form submits the wanted rows — `tech_id` + `tech_role` in display order — and `saveTechs()` reconciles them with the stored junctions by technology, so a save retried after a partial failure converges instead of replaying stale deletions or duplicating a junction).

**Async saves — why a failed save never empties a form.** Every `form[data-async]` is sent with `fetch` by `src/lib/admin/runtime.ts` (loaded by `AdminLayout`) with the `x-admin-async: 1` header; the page then answers JSON through `formResponse(result)` (`{ ok, redirect }` or a 422 `{ ok: false, error, fields }`) instead of re-rendering. The DOM is never replaced, so typed values, the files picked in file inputs (a browser can never re-fill those) and the islands' unsaved state survive an error. Without JS the same forms post natively and the page re-renders with the submitted `values`. `fields` maps a **control's `name`** to its problem: PocketBase column errors are renamed through `ScopedError` (e.g. the English translation row's `name` → `name_en`), and checkbox groups / island lists are targeted by a `[data-field="<name>"]` wrapper. The runtime also does client validation (French messages, `data-required-group`), the problems panel, per-field "modified" marks, the leave-page warning and ⌘S / Ctrl+S. Gotcha: never read `form.action` in client code — the hidden `<input name="action">` shadows it.

The back-office has its own visual system in `src/styles/admin.css` (an editor workbench: explorer, problems panel, status bar whose colour is the save state), deliberately separate from the public design tokens.

`adminMiddleware` (in `src/middleware.ts`, runs after `userMiddleware`) gates every `/admin*` route: redirects to `/admin/login` when logged out, and away from the login page when already logged in. English fields are optional and filled in manually in the back-office; when left empty, the public site falls back to the French text (see `localize()` in `src/data/projects.ts` and `getReviews()`).
